# Manual QA run — 14 November 2026

A full pass through the app as a new user, checking the database after each
action rather than trusting the screen. Six defects found, all fixed.

Conditions: the upstream provider (Jikan) was **completely unreachable** for
the whole run, while MyAnimeList itself answered normally. That turned out to
be useful — it exercised every degraded path at once.

---

## Defects found

### 1. A missing GPU took down the whole app — *critical*

```
THREE.WebGLRenderer: A WebGL context could not be created.
```

The decorative background threw during render, which in React means the entire
page fails. The sign-in form was replaced by a crash screen.

Anyone with hardware acceleration disabled, an older machine, a locked-down
work laptop or certain VMs would have seen this instead of the app. It checked
`prefers-reduced-motion` — a *preference* — but never whether WebGL actually
*worked*, which is a *capability*.

**Fixed** with a capability probe, an error boundary, and runtime
context-loss handling. Any failure now falls back to a CSS gradient.

### 2. Adding a title took 13 seconds and then failed — *critical*

```
POST /api/v1/library 503 in 13.4s
```

Search results carry our internal UUID; the add endpoint only accepted a
*provider* ID. The client sent the UUID, the lookup missed, and the server went
to the network for **a title already in its own database** — then failed,
because the provider was down.

`docs/API.md` claimed the search `id` was a provider id. The code never did
that. The contract and the implementation had quietly disagreed since the
endpoint was written.

**Fixed** by accepting the internal `workId` (preferred) or a `providerId`.
**13.4s → 108ms**, and adding now works during an outage.

### 3. Client-side writes never refreshed the session — *high*

Access tokens last 15 minutes. The browser client had no refresh-on-401, so
after fifteen minutes idle, marking an episode silently failed and the tick
reverted. For a tracker, losing the user's input is the worst possible bug.

**Fixed** with refresh-and-retry in the API client, behind a single-flight
lock — because refresh tokens rotate, and two parallel refreshes would present
an already-used token, which the server correctly treats as theft and signs you
out everywhere.

### 4. An expired session made your library look deleted — *high*

The series page used an optional session check, so an expired token rendered it
as if signed out: every season at 0 progress, no controls. Indistinguishable
from data loss.

**Fixed** — the page now requires a session like every other. There's no
sharing feature, so a public series page served nobody.

### 5. One failed refresh signed you out permanently — *medium*

The session route cleared auth cookies on *any* error. A momentary database
blip would delete the refresh cookie, after which every later attempt
short-circuited on "no token" — making a perfectly valid 60-day session
unreachable.

**Fixed** — cookies are cleared only when the token is definitively dead
(expired, revoked, replayed). A transient failure costs one retry, not the
session.

### 6. "Next season" with no way to start it — *medium*

The series page said **"NEXT SEASON — Episode 1"** for a season that wasn't in
the library, then rendered a dead `0/12` bar and no button. The app named the
thing to do and refused to let you do it.

Worse, `0/12` is actively misleading: it reads as "you've watched none of it"
when the truth is "this isn't in your library".

**Fixed** — an **Add** button, and honest text: *"12 episodes · not in your
library"*.

## Performance

Every search during an outage waited out the full retry budget before falling
back — ~13 seconds each. The fallback worked; it just felt broken.

**Fixed** with a circuit breaker plus a shorter interactive budget. A provider
that fails twice is skipped for 60 seconds, and one success closes the circuit
again.

| | Before | After |
|---|---|---|
| 1st search, provider down | 12.8s | 4.2s |
| 2nd | 12.8s | 4.0s |
| 3rd onwards | 12.8s | **0.02s** |

## Verified working

Checked against the database, not the screen.

**Accounts** — passwords stored as argon2id, refresh tokens stored hashed
(never plaintext), 60-day expiry.

**Isolation** — a second account saw **zero** rows while the first had eight,
with 17 shared catalog titles visible to both. The catalog is shared; user data
is not.

**Session recovery** — dropped the access cookie to simulate expiry; the next
request bounced through the refresh route and landed back on the original page.

**The full watch lifecycle:**

| Step | status | progress | rewatching | rewatch_count | sessions |
|---|---|---|---|---|---|
| add | planned | 0 | — | 0 | 0 |
| watch 5 | **watching** | 5 | — | 0 | 1 |
| complete | **completed** | 12 | — | 0 | 1 |
| start rewatch | completed ✓ | **0** | **yes** | 0 | 2 |
| finish rewatch | completed | 12 | — | **1** | 2 |

Status correctly stays `completed` through a rewatch, and `rewatch_count` is
incremented by a database trigger rather than application code.

**Derived data** — `nextUp` correctly advanced from "START HERE · Episode 1" to
"NEXT SEASON · Episode 1" after season 1 was completed. Unaired entries render
with a dashed marker, no progress bar, and *"No release date announced"* — no
invented dates anywhere.

## Still open

- **Offline queue.** Protocol and server are done; the browser doesn't yet
  persist unsent changes, so a write made with no connection is lost rather
  than deferred.
- **Live add untested.** Jikan has been unreachable across two sessions, so
  adding a title the catalog has never seen has never been exercised
  end-to-end. Needs a `MAL_CLIENT_ID` to test properly.
- **Notifications** are recorded but never delivered.
- **Filler data** and **cover-art colour sampling** remain unimplemented.
